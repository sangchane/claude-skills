# 기존 화면 개선 — 감사 절차 (Audit an existing screen)

> "엉망이다·지저분하다·AI 같다"는 지적을 받은 **이미 있는 화면**을 고칠 때 읽는다. 새 화면은 SKILL.md 1~3절부터.
> 감으로 전부 뜯어고치면 기능이 깨지고 다음 지적이 또 나온다 → 찍고, 재고, 3개만 고치고, 다시 찍는다.
> 출처: Leonxlnx/taste-skill `references/critique.md` §1·§4~§6, `redesign-skill/SKILL.md`(MIT, ★9.6만, 2026-10-14 확인). 랜딩 전용 패스(로고 가리기·사진 수·경쟁사)는 뺐다.

## 1. 먼저 찍는다

- 데스크톱 1440×900과 폰 390×844로 현재 화면을 스크린샷하고 Read로 본다(쓸 수 있는 브라우저 도구·Playwright). 고치기 전 사진이 없으면 나아졌는지 말할 수 없다.
- 사용자가 지목한 화면·구성요소(예: "시세 차트")가 있으면 그 부분 확대 샷도 찍는다.

## 2. 패스 — 하나씩 따로 본다 (섞지 않는다)

1. **1초.** 보고 눈을 뗀다. 무엇을 봤나? 답이 하나여야 한다(그 화면의 결론·핵심 지표·지도). "화면"이라고밖에 못 하면 초점이 없다.
2. **실눈.** 글자가 회색 막대로 보일 때까지 흐리게 본다. 크기 차이가 분명한 덩어리 2~3개로 줄어야 한다. 비슷한 작은 덩어리가 많으면 전부 중간 크기라 아무것도 이끌지 않는다.
3. **시작선.** 패널마다 텍스트 블록의 왼쪽 가장자리 x 위치를 센다. **패널당 3개 이하**가 정상. 6개면 요소를 하나씩 따로 놓은 것이다.
4. **간격.** 관련된 것은 가깝고 무관한 것은 먼가? 패널·섹션 사이 간격이 그 안의 어떤 간격보다 큰가? 제목 위 간격이 아래 간격의 2배 이상인가? 우연히 빈 곳(구멍)이 있나?
5. **글자.** 글자 크기가 **5개를 넘나**? 한 줄이 75자를 넘거나 3줄 넘게 가운데 정렬인가? 숫자가 `tabular-nums`로 정렬돼 있나?
6. **색.** 면적을 가장 많이 차지하는 색 · 받치는 색 · 강조색을 이름 붙인다. 강조색이 10곳에 있으면 아무 뜻이 없다 — **주요 행동 1곳 + 디테일 1곳**이어야 "여기"가 된다. 상태색(통과·주의·위험)은 강조색과 별개 쌍인가?
7. **차트·지도.** `patterns/charts.md` 체크와 `legend-annotation.md` 체크를 돈다.
8. **충돌.** 제목·숫자·버튼 위에 겹친 것이 있나? 폰에서 화면 밖으로 나가거나 가로 스크롤이 생기나?
9. **같은 모양 반복.** 섹션마다 레이아웃을 한 단어로 적는다(카드 격자·표·목록·막대). 같은 단어가 연달아 3번이면 템플릿이 보인다.
10. **모션.** `motion.md` "AI 티 모션 점검"의 임계값을 센다.

## 3. 기록 — 상위 3개만

```
ROUND n
상위 문제 3개(가장 눈에 띄는 것부터), 각각 보이는 스크린샷과 고칠 방법:
1. 시세 차트: 건수 막대가 가격 선과 같은 높이·채도로 겹쳐 선이 안 읽힘 (desktop-l52.png) → 막대를 아래 25%·옅게
2. …
3. …
```

- 동료 디자이너에게 말하듯 위치·수치로 쓴다("요약 문단이 제목보다 40px 왼쪽에서 시작"). "더 다듬을 수 있음"은 문제가 아니다.

## 4. 고치는 순서 — 앞이 틀리면 뒤로 못 살린다

1. **위계** — 화면당 주인공 하나. 큰 것을 더 크게, 작은 것을 더 적게.
2. **구성·간격** — 공유 시작선, 패널 간격, 구멍.
3. **글자** — 크기 대비, 줄바꿈, 줄 길이.
4. **색** — 비율과 강조색 절제.
5. **상태·디테일** — 빈·로딩·에러, 포커스, 작은 정렬, 폰 다듬기.
6. **모션** — 마지막.

뭔가 지워 빈자리가 생기면 장식으로 채우지 않는다. 간격을 닫거나, 남은 핵심을 키우거나, 접는다.

## 5. 지키는 것 (사용자가 요청하지 않으면 바꾸지 않는다)

- 스택(프레임워크·스타일 방식), 라우트·URL, API 필드명, 요소 id·테스트 셀렉터, 기존 접근성 성과(포커스 링·대비).
- 새 라이브러리는 의존성 파일을 먼저 확인한다. 변경은 작게, 변경마다 테스트·스크린샷.
- 프로젝트 DESIGN.md·테마 토큰이 있으면 그 안에서 고친다(SKILL.md "디자인 기준").

## 6. 멈출 때

- **최대 3라운드**: 패스 → 상위 3개 수정 → 다시 찍기 → 패스. 낯선 사람이 알아챌 문제가 없으면 일찍 멈춘다.
- 3라운드 후에도 남은 문제는 숨기지 말고 그대로 보고한다(무엇이 남았고 왜 못 고쳤나).
- 고친 결정의 근거(빌린 패턴·버린 대안)는 DESIGN.md(없으면 SPEC)에 몇 줄 남긴다.
