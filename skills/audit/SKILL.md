# dev:audit — 고치기 전에 보고서부터

세 점검 모두 **보고서가 먼저**다. 결론(무엇을 하자)을 첫 줄에, 근거는 `파일:줄`·명령 출력으로 붙인다.
보고 뒤 고치는 일은 `dev:build` 경로로 넘긴다(구조를 바꾸는 고침은 build 「리팩토링」 경로 — 버그 확률을 재고 나서).
볼트·그래프가 있는 프로젝트는 이미 정리된 결론부터 본다(rules 「문서 지도」).

## ① 상태 머신 헌터

목표: 기존 기능을 깨지 않고 UX·DX·AX 셋 모두를 올리는 결정. 셋 중 하나를 올리려고 다른 하나를 깎는 안은 고르지 않는다.

1. **후보 찾기** — 아래 신호를 grep 으로 훑고, 화면·서버·DB·작업 큐를 모두 본다.
   - 한 대상에 붙은 불리언 여러 개: `isLoading`·`isError`·`isOpen`·`done`·`busy`·`pending`·`ready`
   - `status`·`state`·`phase`·`mode`·`step` 문자열·숫자 필드, 같은 문자열 리터럴을 여러 파일에서 비교
   - null 이 상태를 뜻하는 칸(`deleted_at`·`paid_at`·`started_at`), 재시도·횟수 카운터, `setTimeout`·`setInterval` 사슬, 플래그 조합 조건(`a && !b`)
2. **후보마다 표 한 행** — 상태 목록, 전이(누가 바꾸나 `파일:줄`), 바꾸는 곳 수, **불가능해야 할 조합이 실제로 가능한가**(예: 로딩 중이면서 오류), 빠진 전이(실패·취소·시간 초과·재진입), 저장·서버와 어긋날 수 있나.
3. **점수 셋** (각 0~3)
   - UX: 사용자가 겪는 깨짐 — 끝나지 않는 로딩, 두 번 눌러 두 번 실행, 새로고침하면 다른 상태
   - DX: 상태를 바꾸는 곳이 흩어져 고칠 때 깨질 곳 수, 읽어서 전이를 알 수 있나
   - AX: 에이전트가 한 파일만 읽고 상태·전이를 알 수 있나, 로그에 상태 이름이 찍히나, 전이 표를 시험이 확인하나
4. **결정** — 후보마다 「고침」 또는 「놔둠 + 이유」. 고치는 꼴은 이 순서로 가장 작은 것:
   ① 불리언 묶음 → 이름 있는 상태 하나(판별 유니언·enum) ② 흩어진 대입 → 순수 함수 `next(상태, 사건) → 상태` 한 곳
   ③ 전이 표를 시험으로 고정(허용 안 된 전이는 실패) ④ 상태 기계 라이브러리는 이미 의존성에 있을 때만.
   셋 다 0~1 이면 놔둔다 — 아무도 겪지 않는 상태를 위해 설계하지 않는다.
5. **보고 → 고침** — 표와 결정을 낸 뒤, 「고침」을 점수 합이 큰 순서로 `dev:build` 리팩토링 경로에 넣어 이어서 한다(사용자가 「보고서만」이라고 했으면 멈춘다).
   기능을 깨지 않는 증거: 고치기 전 동작을 시험으로 고정하고, 고친 뒤 같은 시험과 같은 출력.

## ② CI 감사관

**코드는 아무것도 고치지 않는다. 보고서부터 낸다.**

1. `python3 -I <이 스킬 폴더>/scripts/ci_audit.py [--repo owner/name] --limit 150 --top 5` — 최근 실행 150번, 작업마다 중앙값(초).
   - 대기 = 기계 할당 대기(job `started_at − created_at`) · 셋업 = 체크아웃·도구·의존성 설치·캐시 복원 단계(끝 정리 단계 포함) · 실행 = 나머지
   - 셋업 분류는 단계 이름으로 한다. 이름이 특이한 준비 단계가 실행에 섞였으면 표 밑에 밝힌다.
2. 보고서: 가장 느린 5개 작업 표(대기·셋업·실행·합계·가장 느린 한 번) → 세 단계 중 어디가 큰지 한 줄씩 → 줄일 수 있는 곳 후보(캐시·러너 크기·작업 나누기)는 **제안만**.
3. `gh` 인증이 없거나 실행 기록이 없으면 그 사실과 명령 출력 한 줄로 끝낸다.

## ③ 재설계자

질문: **오늘 같은 목표로 처음부터 다시 시작한다면, 지금 코드에서 여전히 남겨야 할 것은 무엇인가.** 보고서만 낸다.

1. 목표 한 장(`docs/goals.md`)과 설계 문서(04 「코드 구조」)를 읽는다. 없으면 README·최근 커밋에서 목표를 세 줄로 적고 그 사실을 밝힌다.
2. 모듈(폴더·큰 파일)마다 재는 것: 목표의 몇 번에 닿나 · 시험이 있나 · 최근 90일 바뀐 횟수와 그중 버그 고침 수(`git log --since=90.days --name-only`) · 의존 방향이 거꾸로인가.
3. 판정 — **남김**(목표에 닿고 시험이 있고 잘 안 깨짐) / **다시 씀**(목표에 닿지만 자주 깨지거나 구조가 막음) / **버림**(목표에 안 닿음). 판정마다 근거 한 줄.
4. 보고서 순서: 남길 것 목록이 맨 앞 → 다시 쓸 것(효과 큰 순 3개, 각 dev:build 카드 한 줄) → 버릴 것.
   경고: 버림·다시 씀은 제안이다. 지우기 전에 사용자에게 묻는다(rules 「삭제 전에만 묻는다」).
