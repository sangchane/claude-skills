# 현업 바닥선 — 사용자가 말하지 않아도 설계에 들어가는 구현 품질 항목

사용자가 기능만 말해도, 아래 항목은 **설계(A2·A4·A5·A7)에서 정하고 구현(dev:build SPEC·REVIEW)에서 대조한다**.
「나중에」로 미루는 것은 허용하지만, 미룬 항목은 언제 할지(어느 단계·조건)를 적는다 — 적지 않은 항목은 빠진 것이다.
이유: 2026-10-17 메이플 — 사용자가 처음에 「현업 방식(레이어·서비스·예외·로그)으로」라고 했는데 그 말이 메모리에만 남고 설계·SPEC 어디에도
들어가지 않아, 새 서버가 한 파일에 연결·세션·규칙·SQL을 다 넣은 채로 만들어졌다. 사용자가 「분명 최초 요구사항에 있었을텐데」라고 다시 말해야 했다.

강도별: **spike**는 1~5만(구조·조립·오류·꼴 검사·로그), **lite**는 1~10, **full**은 전부. 서버·DB가 없는 정적 도구면 해당 없음 + 사유.

| # | 항목 | 설계에서 정할 것(문서·절) | 사용자 말 없을 때 기본값 | 구현에서 확인 |

## A2에서 쓰는 법

`02-blindspot-register.md` 12축 「현업 바닥선」 아래에 항목 1~17을 한 행씩 Clear/Assumed/Asked로 마킹한다. 대부분은 위 기본값으로 **Assumed** —
사용자에게 묻는 것은 운영 환경이 기본값을 깨는 경우뿐(예: 폐쇄망이라 백업처가 없음, 규제로 로그 보존 기간이 정해짐).
「나중에」로 미루는 항목은 `Assumed — 미룸: <언제>`로 적는다.

## 기존 프로젝트(설계 없이 이미 구현 중)

dev:build가 SPEC을 쓸 때 04에 「코드 구조」 절이 없으면, 그 SPEC의 첫 작업으로 지금 코드를 읽어 이 표 1~10을 04에 세우고
프로젝트 AGENTS.md 규약에 한 줄로 올린다(매 세션 읽히게). 메모리에만 두지 않는다. 미룬 11~17은 04 「코드 구조」 끝 「남은 바닥선」 표에 언제 할지와 함께.
